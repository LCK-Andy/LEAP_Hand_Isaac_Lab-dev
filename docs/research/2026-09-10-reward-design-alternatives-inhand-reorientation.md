# Reward-Design Alternatives for Generalized In-Hand Object Reorientation

**Date:** 2026-09-10
**Scope:** Alternatives to manual reward-function tuning for `Isaac-Repose-Objects-LEAP-Direct-v0` (LEAP hand, 16 DOF, per-episode resampled YCB catalog, target-orientation goals with hold-to-confirm, 136-d obs + 12 tactile force channels, Isaac Lab 3.0 / Isaac Sim 6.0, FlashSAC + RSL-RL PPO, 1024 envs on a 12 GB laptop GPU).
All paper claims below were verified against arXiv abstract/HTML pages on 2026-09-10; repo-specific numbers marked *estimate* use the internal 1024-env benchmark (~32.5–36.6 ms/step, from `scripts/bench_collision_proxy.py`).

## Executive summary

The working hypothesis is **confirmed**: the modern generalizable in-hand rotation line (OpenAI Dactyl → Hora → RotateIt → AnyRotate) trains on **one simple task term (orientation progress or angular-velocity alignment) plus 3–6 regularizers and at most a 1–2-parameter curriculum**; generalization comes from massive object/physics randomization, not from elaborate reward shaping (Section 2). None of these works gates reward terms on measured fingertip forces — tactile data enters *observations*, not rewards. The most directly applicable modern answer to "manual reward iteration is not efficient" is **LL-automated reward search (Eureka family)**, which now has (a) an official Isaac Lab implementation targeting exactly this repo's task class — `IsaacLabEureka` supports `DirectRLEnv` + RSL-RL/RL-Games — and (b) a published, successful application to *tactile multi-axis in-hand rotation*: Text2Touch (CoRL 2025) beat a carefully tuned human reward with LLM-written rewards an order of magnitude simpler. Secondary levers: DexPBT-style population-based tuning of reward *coefficients*, and AnyRotate-style performance-scheduled goal/curriculum parameters. VLM-based and demo-based rewards are a poor fit for state-based 1024-env training.

## 1. LLM-automated reward design (Eureka family)

**How it works.** An LLM writes dense reward *code* against the environment's exposed variables; several candidates are trained in parallel; policy performance (a task `success_metric`) is fed back as text ("reward reflection") and the LLM iterates — an evolutionary outer loop around GPU-parallel RL. No task-specific prompting or reward templates are needed ([Eureka, arXiv:2310.12931](https://arxiv.org/abs/2310.12931), ICLR 2024).

**Key papers:**
- **Eureka** ([arXiv:2310.12931](https://arxiv.org/abs/2310.12931), ICLR 2024; [project](https://eureka-research.github.io/), [code](https://github.com/eureka-research/eureka)). GPT-4 evolutionary reward-code search over 29 Isaac Gym environments / 10 robot morphologies, incl. Shadow-Hand pen spinning (with curriculum); beats expert humans on 83% of tasks, +52% average normalized improvement. Demonstrated dexterity + Isaac Gym from the start.
- **Text2Reward** ([arXiv:2309.11489](https://arxiv.org/abs/2309.11489), ICLR 2024; [project](https://text-to-reward.github.io/)). Dense *shaped* reward code from natural-language goals, with iterative feedback; 13/17 ManiSkill2/Meta-World tasks match or beat expert-written rewards. Manipulation but not dexterous/in-hand.
- **DrEureka** ([arXiv:2406.01967](https://arxiv.org/abs/2406.01967), RSS 2024; [project/code](https://eureka-research.github.io/dr-eureka/)). Extends the loop to jointly synthesize **reward + domain-randomization ranges** for sim-to-real (quadruped and dexterous tasks) — relevant later when this repo moves to hardware.
- **REvolve** ([arXiv:2406.01309](https://arxiv.org/abs/2406.01309), ICLR 2025; [project](https://rishihazra.github.io/REvolve)). Evolutionary reward refinement guided by human feedback; evaluated on autonomous driving, humanoid locomotion, and dexterous manipulation.
- **Text2Touch** ([arXiv:2509.07445](https://arxiv.org/abs/2509.07445), CoRL 2025; [project](https://hpfield.github.io/text2touch-website/)). **The critical precedent:** Eureka-style LLM reward search applied to **tactile multi-axis in-hand object rotation** (Allegro hand + TacTip vision-based tactile sensors, Isaac-Gym-style training, sim-to-real distillation). Screened ~2,000 LLM-written rewards (5 LLMs: GPT-4o, o3-mini, Gemini-1.5-Flash, Llama3.1-405B, Deepseek-R1; short 150M-step runs; finalists 8B steps). Results: all five LLMs' rewards beat a carefully tuned human baseline in rotation speed/stability, in sim, out-of-distribution, and on the real hand (best: +38% real-world rotation). LLM rewards used ~5–12 variables vs the human baseline's 66 (≈1/4 the code). Two transferable prompt lessons: (1) give the success bonus and termination penalty to the LLM as *scalable variables* (without this, nearly all runs scored 0%), (2) list all 70+ environment variables explicitly in the reward signature. No code released as of the arXiv page.
- **IsaacLabEureka** ([github.com/isaac-sim/IsaacLabEureka](https://github.com/isaac-sim/IsaacLabEureka), NVlabs, Apache-2.0). Official Eureka port **for Isaac Lab `DirectRLEnv` tasks**, supporting RSL-RL and RL-Games, OpenAI/Azure APIs, parallel candidate training on one GPU, winner selected by the task's `success_metric`. Referenced by the Isaac Lab docs as the recommended LLM-reward pipeline for direct workflows.

**Compute cost.** Eureka's abstract states no cost; Text2Touch quantifies the pattern: many cheap screening runs (150M env steps each) + few full runs (8B steps). For this repo: 150M env steps ≈ 146k control steps at 1024 envs × ~36 ms/step ≈ **~1.5 h GPU per candidate** (*estimate*), i.e. a 5-candidate × 5-iteration search ≈ 35–40 h wall-clock (*estimate*) — feasible overnight×2 if candidates are shortened to 50–100M steps.

**Fit for this repo.** Very good. The env is already a `DirectRLEnv` with an `rl_games`/`rsl_rl` path; the reward is already pure code over exposed tensors. The search loop must run on RSL-RL/RL-Games (IsaacLabEureka does not support FlashSAC), but the *found reward* is runner-agnostic — drop it into `compute_leap_rewards` and fine-tune with FlashSAC. Provide the LLM the full variable list (proprio, object pose/vel, per-tip forces, goal axes) and expose success/termination scales as variables (Text2Touch's lesson). Define a strict `success_metric` (e.g., rotations-to-goal within tolerance / hold-to-confirm rate).

## 2. What rewards do the modern in-hand reorientation works actually use?

Verified reward structures (term: weight where stated):

| Work | Reward | Curriculum / tricks |
|---|---|---|
| OpenAI Dactyl block ([arXiv:1808.00177](https://arxiv.org/abs/1808.00177)) | per-step progress `d_t − d_{t+1}` on angle to goal; **+5** per goal reached (<0.4 rad); **−20** drop | goal resampling; PPO, MuJoCo, 6,144 rollout cores + 8 V100s |
| OpenAI cube / ADR ([arXiv:1910.07113](https://arxiv.org/abs/1910.07113)) | same dense-progress + sparse bonus/penalty structure | **ADR** = automatic curriculum over randomization ranges; 64 V100s, months |
| Hora ([arXiv:2210.04887](https://arxiv.org/abs/2210.04887), CoRL 2022) | `clip(ω·k̂, ±0.5)`; pose dev −0.3; linvel −0.3; work −2.0; torque −0.1 | **none** — full randomization from step 0; RMA teacher-student (privileged 8-d extrinsics regressed from 30-step proprio history); Isaac Gym, 16,384 envs |
| RotateIt ([arXiv:2309.09979](https://arxiv.org/abs/2309.09979), CoRL 2023) | Hora terms + undesired-axis velocity −‖ω×k‖₁ (λ: 0 → −0.1) | 1-coefficient curriculum; single-axis RL oracles → multi-axis distillation (pure multi-axis RL did not converge); teacher: PointNet shape + physics + pose; student: touch (contact locations) + depth + proprio transformer; 32,768 envs; EGAD/GSO/YCB/ContactDB objects |
| AnyRotate ([arXiv:2405.07391](https://arxiv.org/abs/2405.07391), CoRL 2024) — closest cousin of this repo (goal = target orientation, tactile fingertips) | keypoint distance 1.0; delta rotation about axis 5.0; sparse goal 10.0; good contact ≥2 tips 0.1; bad contact 0.2; ω pen 0.5; pose pen 0.5; work 0.1; torque 0.05; termination 50 | adaptive λ on (contact+stable) terms growing with rotations/episode; goal increments of 30° (angular-velocity reward **failed** in multi-axis goal setting); teacher-student; touch = binary contact + contact pose + force magnitude in **observations**; 8,192 envs |
| DexPBT ([arXiv:2305.12127](https://arxiv.org/abs/2305.12127), RSS 2023) | reach/pick/target progress terms + joint-vel penalty, sequentially active | PBT population evolves reward *coefficients* + PPO hyperparams (see §6) |
| Qi et al. skill composition ([arXiv:2501.05439](https://arxiv.org/abs/2501.05439); [project](https://dexhier.github.io)) | motivated *by* avoiding per-task reward engineering: hierarchically compose learned rotation skills; object pose estimated from proprio + skill predictions | skill-selection meta-policy |
| DexTrack ([arXiv:2502.09614](https://arxiv.org/abs/2502.09614), ICLR 2025; [code](https://github.com/Meowuu7/DexTrack)) | replaces task reward with **tracking of human hand-object references** (RL + imitation "data flywheel") | needs human reference motions — absent for LEAP+YCB repose |

**Verdict.** CONFIRMED: task term + a handful of regularizers (pose, linvel, work, torque) + a 1–2-parameter curriculum, with object shape/physics randomization and teacher-student privileged distillation doing the generalization work. Two nuances: (a) for *goal-orientation* (not continuous-rotation) tasks, AnyRotate needed contact-quality terms and a termination penalty beyond Hora's set — i.e. this repo's term count is not absurd, but its *force-gated* bonus/penalty structure (c8/c9/c10) has no counterpart in the literature; (b) multi-axis goal reaching did not train from an angular-velocity reward anywhere — goal-progress/keypoint-distance formulations were required.

## 3. Learned / VLM success rewards

**How it works.** Reward = similarity of rendered image to a text goal (zero-shot VLM scoring) or a reward function learned from VLM preference queries over image pairs.

- **VLM-RM** ([arXiv:2310.12921](https://arxiv.org/abs/2310.12921), ICLR 2024; [project](https://sites.google.com/view/vlm-rm)): CLIP-style zero-shot reward from a single sentence; demonstrated only on MuJoCo humanoid pose tasks; authors note VLM spatial-reasoning weakness and that quality scales with VLM size.
- **RL-VLM-F** ([arXiv:2402.03681](https://arxiv.org/abs/2402.03681), ICML 2024 per arXiv comments — an ACM listing ties it to NeurIPS 2024; listings conflict; [code](https://github.com/yufeiwang63/RL-VLM-F)): VLM ranks pairs of observations → learned reward network → RL; rigid/articulated/deformable manipulation. Requires many VLM queries on rendered image pairs during training.
- **Genima** ([arXiv:2407.07875](https://arxiv.org/abs/2407.07875), CoRL 2024; [project](https://genima-robot.github.io/)): **not a reward method** — a diffusion model fine-tuned to *draw joint-action targets on images* for behavior cloning (RLBench + 9 real tasks). Included to correct its frequent mislabeling as a visual-reward approach.

**Fit for this repo.** Poor. These methods need rendered images per training state; this task trains state-based at 1024 envs with rendering disabled (and the 12 GB GPU cannot afford per-step image inference at that width). The task's success is *exactly measurable from simulator state* (orientation error), so a VLM would add noise and cost to a signal the env already knows precisely. Plausible niche use: VLM-based automatic *evaluation* of emergent grasp quality on rendered eval episodes — not a training reward.

## 4. Reward-free / goal-conditioned alternatives

- **Hindsight relabeling (HER)** ([arXiv:1707.01495](https://arxiv.org/abs/1707.01495)): relabel failed episodes with achieved states as goals, enabling learning from sparse rewards with any off-policy algorithm (FlashSAC qualifies). For goal-*orientation* tasks the reward is already dense (orientation error is computable from any state), so HER's main benefit is moot; a partial variant — relabeling toward achieved orientations to densify success experience — is possible but unproven in this literature.
- **DexHandDiff** ([arXiv:2411.18562](https://arxiv.org/abs/2411.18562), CVPR 2025; [project](https://dexdiffuser.github.io/)): interaction-aware diffusion planning over joint hand-object states, with LLM-generated guidance functions; includes block re-orientation; 59.2% vs 29.5% on OOD goals. Planning/data-driven, not massive-parallel RL; needs interaction datasets.
- **DexMimicGen** ([arXiv:2410.24185](https://arxiv.org/abs/2410.24185), ICRA 2025; [project/datasets](https://dexmimicgen.github.io/)): synthesizes 21K demos from 60 human demonstrations for bimanual dexterous imitation learning — removes reward design by removing RL, but requires human demonstration sources.
- **DexTrack** (§2): reward replaced by human-reference tracking; same data prerequisite.

**Fit for this repo.** Low. No human reference/demonstration corpus exists for LEAP-hand YCB repose, and creating one (teleop or motion retargeting) is a larger project than the reward problem it would solve. None of these *fully* avoids specifying an objective; they move it into data.

## 5. Tactile-first approaches (relevant to the planned real pulp sensors)

- **RotateIt** (§2): touch = discretized contact locations + finger index, fed to a transformer student that regresses the privileged object encoding. Reward unchanged from Hora's.
- **AnyRotate** (§2): touch = binary contact, contact pose, force magnitude in observations; contact *counts* (not forces) drive two small reward terms (good/bad contact).
- **T3** ([arXiv:2406.13640](https://arxiv.org/abs/2406.13640), CoRL 2024; [code/checkpoints](https://t3.alanz.info)): pretrained tactile transformer across 13 sensors / 11 tasks (3M-image FoTa dataset); as a frozen encoder it gives +25% insertion success vs scratch encoders (+53% vs no touch). Observation-side, policy-agnostic (works with RL or IL).
- **UniTouch** ([arXiv:2401.18084](https://arxiv.org/abs/2401.18084); [project](https://cfeng16.github.io/UniTouch/); CVPR 2024 per project page, not stated on arXiv): binds touch embeddings to CLIP image space via learnable sensor tokens; zero-shot tactile understanding (grasp prediction, touch QA).
- **Tac2Motion** ([arXiv:2509.17812](https://arxiv.org/abs/2509.17812), Humanoids-2025 workshop submission): the rare work using tactile signals *in the reward* (contact-aware shaping for firm grasp + finger gaiting) alongside tactile embeddings in observations; Shadow hand lid-removal; workshop-level evidence.
- Purely-tactile in-hand manipulation ([arXiv:2407.18834](https://arxiv.org/abs/2407.18834)) shows touch-only control is feasible.

**Fit for this repo.** The literature supports the current design: tactile data belongs in observations (the 12 pulp-force channels), while the reward stays task-term + regularizers. The repo's force-gated reward terms (c8/c10 press-bonus, c9 palm-pin) are more aggressive than anything published — if they fight the hold-to-confirm logic (the FlashSAC hook overwriting `success_tolerance`), the literature says they are not needed. When real pulp sensors arrive, a T3/UniTouch-style pretrained encoder over the 4×3 force channels (or real tactile images) is the evidence-backed upgrade path.

## 6. Automatic curriculum / reward scheduling

- **ADR** ([arXiv:1910.07113](https://arxiv.org/abs/1910.07113)) — already implemented in this repo; performance-gated boundary expansion.
- **RotateIt / AnyRotate schedules**: single-coefficient curricula keyed to training performance (λ_rotp 0→−0.1; λ_rew scaling with rotations/episode). Cheap, directly analogous to the repo's existing ADR hooks (`consecutive_successes`, `z_rotation_steps`, `mean_episode_length`).
- **TSCL** ([arXiv:1707.00183](https://arxiv.org/abs/1707.00183)) and **ALP-GMM** ([arXiv:1910.07224](https://arxiv.org/abs/1910.07224); [code](https://github.com/flowersteam/teachDeepRL)): teacher algorithms that sample task parameters (goal axes, increments, object subsets) of intermediate absolute learning progress — a principled replacement for hand-set goal-increment ladders.
- **DexPBT** ([arXiv:2305.12127](https://arxiv.org/abs/2305.12127), RSS 2023; [code](https://sites.google.com/view/dexpbt)): population (8–32 agents) trained in parallel in Isaac Gym (8,192 envs per 16 GB V100 — hardware comparable to this repo); PBT evolve-and-exploit cycles tune PPO hyperparameters **and reward coefficients**; in the reported best agent every reward coefficient drifted upward from its human initial value (e.g. success 1000→1322.7), demonstrating that hand-set weights were not optimal. Note: the installed Isaac Lab 3.0.0b2 has **no PBT module** (checked the local `site-packages/isaaclab` tree); a newer-docs PBT page exists but 404s — porting would follow DexPBT's rl-games-based release.

**Fit for this repo.** Good. The existing ADR scheduler can additionally automate (a) goal rotation increments (AnyRotate's 30°-increment finding) and (b) reward-coefficient ramps, replacing per-session manual tuning with performance-gated schedules. Full PBT multiplies GPU memory pressure (populations × 1024 envs) — viable only at reduced per-agent env counts.

## Recommendations (ranked, most practical first)

1. **Run IsaacLabEureka on the RSL-RL path; transfer the winning reward to FlashSAC.** Effort: ~1–2 days integration (install extension, define `success_metric`, expose a variables-list + scalable success/termination scales in the prompt — Text2Touch's two critical prompt lessons) + ~2–4 GPU-days of screening at 50–100M steps/candidate, 3–5 candidates × 4–5 iterations (*estimate*). Precedent: Text2Touch beat a carefully tuned human reward on the same task class with 10× simpler rewards; IsaacLabEureka already supports this repo's exact env style. The final reward code drops into `compute_leap_rewards` unchanged for FlashSAC fine-tuning.
2. **First, restructure the reward to the literature baseline** (Section 2): keypoint/orientation progress + sparse success + drop/termination penalty + pose/linvel/work/torque regularizers + good/bad *contact-count* terms; delete or observation-ify the force-gated c8/c9/c10 terms; add an AnyRotate-style adaptive schedule on the contact/stability coefficients and goal increments (hooks already exist in the ADR machinery). Effort: ~1 day, no new dependencies. This is also the honest baseline that path 1 must beat.
3. **DexPBT-style PBT over reward coefficients** if LLM search is unattractive (no API dependency): population 4–8 at 256–512 envs each on the 12 GB GPU; auto-tunes all ~10 coefficients. Effort: ~1 week to port PBT bookkeeping onto the rl-games/RSL-RL loop (no PBT in Isaac Lab 3.0.0b2).
4. **Defer**: VLM rewards (need rendered images; redundant given exact sim-state success) and demo/diffusion methods (no human reference data for LEAP+YCB repose). Revisit T3-style tactile pretraining when the real pulp sensors land.

## Addendum (2026-09-10, later same day): the goal is bigger than repose

The user clarified the overarching objective: the repose policy is an **excitation / data-collection behavior for estimating the object's inertial properties** (mass, COM, inertia tensor). The estimator lives in the sibling repo `~/Documents/Estimate_weight_distribution` (private GitHub `LCK-Andy/Estimate_weight_distribution`): YCB PLY meshes → Gmsh tetrahedral volume meshes → synthetic non-uniform density fields (6 strategies; 90-entry ground-truth manifest of m/COM/I over 15 objects) → simulated contact scenarios (CVXPY SOCP static equilibrium with friction cones, perturbed to produce accelerations) → robust (Huber) least-squares estimation of θ = [m, d=m·c, I(6)]. Its observability rules: mass trivial; COM needs non-collinear gravity directions; inertia needs angular-acceleration diversity (α spanning ℝ³).

This **revises the recommendations above**:

- Recommendation 2's "delete the force-gated c8/c9/c10 terms" is **wrong for this objective**. Section 2's finding (no published in-hand rotation work gates rewards on measured forces) stands, but those works optimize repose only. Here the policy must be *informative*, not just successful — the correct framing is multi-objective: task reward + measurement-quality reward. The env's structure already fits the estimator: hold-to-confirm segments are quasi-static (α≈0, identify m/COM), reorientation transients are α-rich (identify I), and goal resampling diversifies the gravity direction in the body frame.
- Direct precedent for the sensor side: **In-Hand Object-Dynamics Inference using Tactile Fingertips** ([Sundaralingam & Hermans, T-RO 2021, arXiv:2003.13165](https://arxiv.org/abs/2003.13165)) — estimates friction + inertial parameters of a grasped object in motion from multi-fingertip tactile forces alone (factor graph, physically-consistent manifolds; works for low-mass objects where joint-torque methods fail).
- The principled modern replacement for hand-crafted press bonuses is an **information-gain reward**: **ASID** ([Memmel et al., ICLR 2024 oral, arXiv:2404.12308](https://arxiv.org/abs/2404.12308)) trains an exploration policy to maximize Fisher information (min trace of FIM⁻¹ over domain-randomized candidate parameters) for system ID. A per-episode version here: reward ∝ reduction in the estimator's uncertainty (e.g., condition/eigenvalue structure of the accumulated regressor A).
- Path 1 (Eureka search) gets *stronger* under this goal: define `success_metric` as task success **and** estimation accuracy — run the sibling repo's LS estimator on each episode's logged forces and score (m, COM, I) error against the manifest ground truth. The LLM then auto-tunes the task/informativeness trade-off that is currently hand-tuned.

Sim-side gaps to close before the loop can run end-to-end (not yet done):
1. The 12 tactile channels read `net_forces_w` = net **normal** force only; Newton–Euler rows need full forces (friction) and contact positions — both are opt-in ContactSensor cfg flags.
2. Object linear/angular accelerations are directly available from the env's object state (no need for the sibling repo's perturbation trick — reorientation dynamics provide real α).
3. The env currently authors uniform density (400 kg/m³) via MassAPI. PhysX `UsdPhysics.MassAPI` also accepts mass, COM offset, and diagonal inertia — per-episode randomized inertial params drawn from the 90-entry manifest (objects overlapping this env's catalog: strawberry, lemon, orange, + cube/sphere) would make the sim's ground-truth distribution exactly the estimator's, closing the loop: policy → logged forces → estimator → manifest comparison.
